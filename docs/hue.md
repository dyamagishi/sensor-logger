# Philips Hue：個々の照明の操作と状態履歴

## 対応範囲

- API v2対応のHue Bridge 1台をローカルHTTPSで利用します。NanoPiからBridgeへの到達性が必要です。
- 個々のデバイスをWeb画面で選択します。Hueのシーン・部屋・ゾーンは取得しません。
- 機器の対応項目だけ、点灯・消灯、明るさ、色温度、色を表示します。複数出力がある機器はカード内で出力別に扱います。
- 消灯中に明るさ・色温度・色を変更すると点灯します。明るさ0%は最低輝度の指定で、消灯操作とは別です。
- 操作確定時に送信し、直後に状態を再取得します。Bridgeが返す状態であり、発光の物理的な測定ではありません。失敗した指示を自動で再実行しません。
- ローカル画面のアクセス権は既存の信頼できるLAN前提です。

## 管理者用設定生成CLI

Mac側でNode.jsを使います。追加のnpm依存はありません。

```sh
npm run hue:setup
# 探索だけを行い、設定生成・ペアリングへは進まない
npm run hue:setup -- --discover
# 別のLANなど、探索範囲を明示する場合（複数指定可）
npm run hue:setup -- --discover --subnet 192.168.53.0/24
# 接続先指定・別ディレクトリへの生成も可能
npm run hue:setup -- --bridge 192.168.53.20 --output .auth/hue-new
```

1. LANインターフェースごとにmDNS（`_hue._tcp.local`、IPv4）とSSDPを並行して繰り返し探索します。ARPの応答済み端末を優先確認し、接続中LANの各IPv4アドレスもHTTPS `/api/config`、必要ならHTTPで調べます。広告だけでは確定せず、HueのBridge識別子・モデルを実応答で検証します。探索範囲・進捗・各方式の候補数・検出結果を表示します。
   - mDNSは約10秒、SSDPは約6.5秒、LAN内応答確認は各アドレスを最後まで調べます。TCP/TLS接続と、その後のAPI応答に別々の待ち時間を設けます。
   - 見つからない場合は待ち時間を延ばして全範囲を再確認します。広告があったのに未確認の候補も再確認します。その後に再探索・手入力・中止を選択できます。
   - VPN・ループバックなどは自動LAN探索から除きます。自動走査は実際のCIDRを使い、/20より広い範囲は除外したことを表示します。`--subnet`で/20〜/32の範囲を明示できます。
   - オンライン検出サービスは使いません。認証情報を送信するのは、後続の証明書確認・ペアリング手順からです。
2. Bridgeの識別情報・接続先・証明書のSHA-256フィンガープリントを表示します。`yes`で信頼する接続先を選びます。
3. Bridgeのリンクボタンを押すよう案内し、ペアリングしてアプリケーションキーを取得します。
4. API v2で個々のデバイスと照明出力を取得して接続確認します。
5. 指定ディレクトリに設定を生成します。既存ディレクトリは上書きしません。

既存キーを再利用する場合は、`HUE_APPLICATION_KEY`環境変数、またはキーだけを記載したファイルを`--key-file PATH`で指定します。キーをコマンド引数やCLI出力に載せません。

| 生成ファイル | 内容 |
|---|---|
| `hue.toml` | Bridge URL・識別子、配置先の証明書・登録ファイルパス |
| `hue.env` | `HUE_CONFIG_FILE`と`HUE_APPLICATION_KEY`のHue専用環境設定断片 |
| `hue-certificate.der` | 明示的に信頼したBridgeの証明書 |
| `README.md` | 配置・既存設定への反映手順 |

出力ディレクトリは0700、各ファイルは0600です。既定の出力先はGit対象外の`.auth/hue`、本体配置先は`/etc/home-sensors`です。`--target-dir /ABSOLUTE/PATH`で配置先を変更できます。CLIは生成だけを行い、転送やサービス再起動は行いません。

接続時は証明書そのものをピン留めし、TLSハンドシェイク署名を検証します。公開CA・IPと証明書名の一致に依存しません。Bridgeの証明書が更新された場合は新しい出力先で設定を再生成します。

## OpenWrtへの反映

既存の[導入・更新手順](deployment.md)に加えて、次を行います。

1. クラウドを使う場合、Hueテーブルを含むマイグレーションを適用し、Workerを更新します。

```sh
npm run cf -- d1 migrations apply home-sensors --remote
npm run cf -- deploy
```

2. 生成した`hue.toml`・`hue.env`・`hue-certificate.der`を`/etc/home-sensors/`へ配置し、root所有・0600にします。
3. 既存の`/etc/home-sensors.env`の末尾に次の行を追加します。クラウドのトークンは保持します。

```sh
. '/etc/home-sensors/hue.env'
```

4. NanoPi側からBridgeへ接続できることを確認し、`cloud.pending=0`のタイミングで新しいサービスを起動します。
5. Web画面の「照明を選択」で対象を選びます。登録情報は`hue-devices.json`へ原子的に保存します。

Macでの接続確認だけでは、NanoPiからの到達性を確認したことにはなりません。初回の実機確認では点灯・消灯、明るさ、色温度、色、壁スイッチによる通信不可の表示、分境界後の記録、毎時のクラウド送信を確認します。

systemdで利用する場合、環境ファイルのシェルの`.`構文は使わず、`EnvironmentFile=/etc/home-sensors/hue.env`を追加します。`--target-dir`はサービスユーザーが登録ファイルを書き込める場所（例：`/var/lib/home-sensors/hue`）にします。

## 記録・履歴

- 起動後と毎分、`device`・`light`・`zigbee_connectivity`を取得して選択した出力を記録します。操作後の追加取得は現在値だけを更新します。
- 分のUnix時刻で記録を識別し、実際の取得時刻も保存します。間隔より短い状態変化や操作元・指示履歴は記録しません。
- 通信できない記録は状態値を`null`にします。画面には最後の確認値と確認時刻を残します。消灯中の明るさ・色は保持設定値です。
- 本体は24時間のRAM履歴・送信待ちキューを保持し、既存センサーと同じ毎時送信に含めます。再起動すると未送信記録が失われます。
- クラウドには1分記録90日、1時間集計5年を保存します。点灯割合は観測できた記録の点灯割合、明るさは点灯中だけの平均・最小・最大、色・色温度は最後の有効値です。取得／取得不可件数も残します。
- 登録解除・Bridgeからの削除後も履歴を残します。「過去の履歴」から参照でき、同じ識別子の再登録では履歴が継続します。
- 識別子はBridge識別子とリソースUUIDから生成します。同じ名前でも異なる機器は別履歴です。

## 検証

```sh
cargo test --locked
npm run test:cloud
npm run test:hue
npx tsc --noEmit
npm run build
sh scripts/build-rust.sh
```

CLIのHTTPS試験ではテスト用証明書を生成するためMac側の`openssl`を利用します。NanoPiの実行時依存には含まれません。

実機を操作しないブラウザ確認用のフィクスチャ：

```sh
npm run build
node tests/hue-ui-fixture.mjs
# http://127.0.0.1:18765/
```
